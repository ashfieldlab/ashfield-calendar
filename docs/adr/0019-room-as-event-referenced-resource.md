# ADR-0019: 회의실(Room)은 캘린더가 아니라 Event 가 참조하는 경량 리소스

- 상태: 채택
- 날짜: 2026-07-12

## 맥락

워크스페이스 회의실(예: 회의실 A/B) 이중예약을 막고 싶다. 같은 방을 같은 시간에 두 회의가
잡으면 안 된다. 현재 `Event.location` 은 자유 텍스트뿐이라 충돌 감지가 불가능하다.

기존 Nextcloud 는 회의실을 **resource 캘린더 / attendee** 로 모델링했는데, 방이 특정
캘린더에 묶이고 설정이 까다로웠다.

## 결정

**Room = 워크스페이스가 관리하는 경량 리소스 목록(`rooms` 테이블).** Event 는 선택적
`room_id` 로 **참조만** 한다. 어느 캘린더의 Event 든 Room 을 점유할 수 있다(캘린더에
묶이지 않음).

- **충돌 감지**: Event 생성과 수정 시 같은 `room_id` 로 시간이 겹치는 다른 Event 가
  있으면 **저장 차단**(hard block) + 충돌 이벤트 정보 반환.
- **관리**: 워크스페이스 관리자가 설정에서 Room CRUD(이름 + 선택적 정원).
- `Event.location` 자유텍스트는 외부 장소용으로 공존.

## 대안

- **(A) resource 캘린더 + 점유 미러링** (Nextcloud 방식): 방을 공유 캘린더로 만들고
  이벤트가 방을 쓰면 방 캘린더에 점유를 복제.: **기각**: 이벤트 생성, 수정, 삭제마다
  미러 동기화가 필요해 "이벤트는 바꿨는데 방 점유는 안 바뀜" 류 버그 표면이 크고,
  방이 특정 캘린더 개념에 묶인다(사용자가 겪은 바로 그 불편).
- **(C) 구조화 라벨만**: 방 목록에서 고르되 충돌 감지 없음.: **기각**: 이중예약
  방지가 이 기능의 핵심 가치.

## 결과

- Room 이 캘린더와 분리돼 어느 이벤트든 참조 가능, 미러 동기화 없음.
- 충돌 체크 = `room_id` overlap 쿼리(기존 겹침 로직 재사용).
- 방 일정 브라우징(캘린더에 방 필터), 공개 BookingType 의 방 충돌 연동은 후속.
- 되돌리기: `rooms` 테이블 + `events.room_id` 컬럼. resource-캘린더로 전환하려면
  마이그레이션 필요하나, 참조 모델이라 데이터 손실 없이 이관 가능.
